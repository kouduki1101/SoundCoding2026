# PRリハーサルの体験設計

## 使う場面

レビュアーが変更を開き、「呼び出す相手が変わったが、何を確認すればよいか」を短時間でつかみたい場面を想定します。最初から大きな譜面やAgentの全調査記録を読ませず、具体的な接点を一つ選んでから詳細に進みます。

1. Web返品か店舗返品を選び、受付関数の呼出先がどう変わったかを読む。
2. 変更前と変更後を同じ長さ・音源で続けて聴く。「呼ぶ→応える→受け取る→重なる」の段階に合わせて、左右の原文が切り替わる。
3. 気になった瞬間の呼出行・返却候補・利用箇所を見て、仕様やテストで確かめる問いを残す。
4. 必要な場合だけ詳細譜面へ進み、音符からコード行へ、コード行から音へ戻る。

最初の画面は「選ぶ」「聴く」「問いを残す」の順に操作を並べています。自動でマニュアルを開かず、操作の結果が隣の根拠コードに出るようにしています。音を使わない人も同じ根拠と問いを読めます。

## 三作品の役割

| 作品 | 統合した強み | レビューでの役割 |
| --- | --- | --- |
| [Code Groove](https://github.com/kdoai/code-groove) | 根拠付きの意味イベント、再現可能な譜面、Agentの調査と構造比較 | 音からソースへ戻れる技術基盤 |
| [SoundCoding2026](https://github.com/kouduki1101/SoundCoding2026) | 関数同士が呼び、応え、受け取る短い音の対話 | 変更を「関数同士の関係」として聴く中心体験 |
| [Codelody](https://github.com/yuki-kobayashi-git/codelody) | カラオケ風の行同期と、行を選んで聴き直す操作 | 違和感の瞬間と原文を結ぶ操作 |

この統合では、音程差を欠陥点数として扱いません。Code Grooveが確認した意味・関係の根拠と、SoundCoding2026の対話表現を揃え、Codelodyの行同期を根拠へ戻るために使います。

## データと限界

公開サイトは保存済みGemini解析を表示する静的デモです。新たなPRの解析、ログイン、Agentへの追加質問はできません。ブラウザ内の問いはローカル保存され、Markdownとしてコピーできます。

ライブ版のAPIは公開GitHub PRのURLを受け取り、解析対象のhead commitを固定します。現状はheadのコードを調べる機能であり、PR差分の自動判定やmerge-baseによる変更前後の構築はしません。デモの前後比較は収録済みの二つの解析を使います。

元のCode Grooveプロジェクト固有の `infra/deployment-config.json` は、このリポジトリへ移していません。ライブ版を配備する際は、権限のあるGoogle CloudプロジェクトとFirebase設定を別途用意します。

静的に呼出関係を一意に解決できない場合は、対話を生成せず理由を表示します。演奏は実行経路・テスト結果・正誤を表しません。レビューの問いは人が仕様とテストで確かめるためのものです。

## 確認

`pnpm build:static`、`pnpm typecheck`、`pnpm lint`、`pnpm test`、`python -m pytest -q`、`pnpm test:e2e` で検証します。外部サービスを使うライブE2Eは、認証と配備先が設定されていない環境ではスキップされます。
